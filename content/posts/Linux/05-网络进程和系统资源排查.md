> [Linux 入门指南](./00-Linux入门指南.md) · 第五章：判断网络、进程和资源问题。

排查问题时，先把“访问不了”或“机器很慢”拆成可验证的现象：地址是否正确、进程是否运行、端口是否监听、请求在哪一步失败、哪类资源持续紧张。

**每条命令只提供一部分证据。** 本篇按网络、进程、资源三个层次组织命令，并给出结果的理解方式。示例以 Linux 为主；服务名、端口和网卡名称应按实际环境替换。

## 一、先理解地址与监听范围

IPv4 地址由四段十进制数字组成，每段为 `0` 到 `255`，例如 `192.168.1.10`。实际配置还需要前缀长度或子网掩码；一个 IP 地址本身不能说明网关和可达范围。

| 地址或名称 | 含义 | 常见用途 |
| --- | --- | --- |
| `127.0.0.1` | IPv4 回环地址 | 访问当前网络命名空间内的服务 |
| `::1` | IPv6 回环地址 | IPv6 本机访问 |
| `localhost` | 通常解析到回环地址的主机名 | 可能对应 IPv4、IPv6，或两者 |
| `0.0.0.0` | 作为 IPv4 监听地址时表示所有本地 IPv4 地址 | 接收发往不同本地 IPv4 地址的连接 |
| `::` | IPv6 未指定地址，常用于 IPv6 通配监听 | 是否兼容 IPv4 取决于套接字与系统配置 |

服务监听 `127.0.0.1:8080` 时，通常只能从同一网络命名空间访问。容器里的 `127.0.0.1` 指向容器自身，并不自动指向宿主机。

监听 `0.0.0.0:8080` 表示接受发往所有本地 IPv4 地址的连接，**不保证其他机器一定能访问**：防火墙、路由、云安全组和端口映射仍可能阻断连接。客户端应访问实际服务器地址，而不是把 `0.0.0.0` 当作服务器地址。

## 二、检查本机地址、路由与名称解析

### 地址与路由

```bash
ip -br addr
ip route
ip route get 192.168.1.20
```

分别查看接口地址概况、IPv4 路由，以及到指定目标的路由选择。重点确认网卡是否启用、地址是否正确、是否存在合适的路由与网关。

`ifconfig` 和 `netstat` 来自传统的 `net-tools` 工具集。已有环境中仍可使用；新接触系统时，可以优先熟悉 `ip` 和 `ss`。

### 主机名与名称解析

```bash
hostname
hostnamectl status
getent ahosts example.com
```

`getent` 按系统名称服务配置查询，结果可能来自 `/etc/hosts`、DNS 等渠道。域名访问失败时，先判断名称能否解析，再判断解析出的地址是否可达。

修改主机名的示例：

```bash
sudo hostnamectl set-hostname web-01
```

本机主机名与公共 DNS 记录是不同配置，修改前者不会自动修改后者。

## 三、测试网络与 HTTP 请求

### ping：测试 ICMP 回应

```bash
ping -c 4 192.168.1.1
ping -c 4 example.com
```

`ping` 可以观察回应、丢包与往返时间，但不能单独证明 Web 服务是否正常。

| 现象 | 可以进一步检查的方向 |
| --- | --- |
| IP 有回应，域名解析失败 | 名称解析配置与 DNS 服务 |
| `ping` 无回应，HTTP 能访问 | 目标或中间设备可能限制 ICMP |
| `ping` 有回应，HTTP 失败 | 应用监听、目标端口、访问控制与协议 |
| 丢包或延迟持续异常 | 网络链路、拥塞、目标负载及 ICMP 限速 |

### curl：查看应用层结果

访问本机示例服务：

```bash
curl --connect-timeout 3 --max-time 10 -i http://127.0.0.1:8080/
```

| 选项 | 作用 |
| --- | --- |
| `-i` | 在响应正文前显示响应头 |
| `-I` | 发送 HEAD 请求，通常只返回响应头 |
| `-v` | 显示连接、TLS 和请求等诊断信息 |
| `--connect-timeout` | 限制连接阶段耗时 |
| `--max-time` | 限制整个传输的耗时 |
| `-f` | 遇到 HTTP 错误状态时返回失败 |

`curl -I` 使用 HEAD 方法，不能完全替代 GET 测试。有些应用不支持 HEAD，或对它采取不同处理。

向测试接口提交 JSON 的格式示例：

```bash
curl --connect-timeout 3 --max-time 10 \
  -H 'Content-Type: application/json' \
  -d '{"name":"demo"}' \
  http://127.0.0.1:8080/api
```

使用 `-d` 时，`curl` 默认采用 POST。接口路径与数据需要按应用定义填写。

| 常见结果 | 通常说明 |
| --- | --- |
| 名称解析失败 | 尚未进入到目标地址的连接阶段 |
| `Connection refused` | 连接被明确拒绝，可能未监听，也可能被访问控制拒绝 |
| 连接超时 | 路由、访问控制、丢包或目标无响应等，需要继续定位 |
| TLS 证书错误 | 已进入 TLS 阶段，应检查证书、域名、信任链与系统时间 |
| HTTP `404` | 已有 HTTP 组件回应，应检查路径与路由配置 |
| HTTP `500`、`502`、`503` | 检查应用或代理日志、上游状态和依赖服务 |

默认情况下，`curl` 收到 HTTP `404` 也可能正常退出。脚本需要把这类状态视为失败时，应明确使用 `-f` 等选项。

## 四、检查端口与监听进程：ss

查看 TCP 和 UDP 监听：

```bash
ss -lnt
ss -lnu
sudo ss -lntp
```

| 选项 | 含义 |
| --- | --- |
| `-l` | 只显示监听套接字 |
| `-n` | 使用数字地址和端口 |
| `-t` | TCP |
| `-u` | UDP |
| `-p` | 显示关联进程，受权限限制 |

精确查看 TCP 8080 端口：

```bash
sudo ss -lntp 'sport = :8080'
```

比起对整行使用 `grep 8080`，端口过滤能减少匹配到其他数字的情况。

需要同时关注监听地址和进程：如果只监听回环地址，外部请求无法直接到达；如果端口被其他程序占用，新程序可能启动失败。

传统命令的对应示例：

```bash
sudo netstat -lntp
```

## 五、查看进程并选择正确的停止方式

### ps 与 pgrep：先确认进程身份

```bash
ps -ef
pgrep -af nginx
```

`ps -ef` 输出中常见字段：

| 字段 | 含义 |
| --- | --- |
| `UID` | 运行用户 |
| `PID` | 进程编号 |
| `PPID` | 父进程编号 |
| `CMD` | 启动命令及参数 |

确认某个进程的状态，下面以 PID `1234` 为例：

```bash
ps -p 1234 -o pid,ppid,user,stat,etime,%cpu,%mem,args
```

`pgrep -af` 会匹配完整命令行，也可能返回多个结果。发送信号前，应确认进程用户、启动参数和用途，不能只凭进程名判断。

### kill：发送信号

```bash
kill -TERM 1234
```

普通 `kill 1234` 默认发送 `SIGTERM`，让进程有机会按自己的处理逻辑退出。

如果进程持续不响应，确认影响后才考虑：

```bash
kill -KILL 1234
```

`SIGKILL`，也就是 `kill -9`，不能被捕获，应用来不及执行退出清理。处于某些不可中断内核等待状态的进程，也不一定立即消失。

对 systemd 托管的服务，通常优先使用：

```bash
sudo systemctl stop nginx.service
```

直接结束服务进程，可能触发管理器自动重启；通过服务管理器停止更符合托管关系。

## 六、查看 CPU、负载与内存

### top：观察整体和进程

```bash
top
```

| 指标或操作 | 理解方式 |
| --- | --- |
| `load average` | 过去 1、5、15 分钟的平均负载 |
| CPU 的 `us`、`sy`、`id` | 用户态、内核态与空闲比例 |
| CPU 的 `wa` | 与等待 I/O 有关的时间比例，需要结合其他指标判断 |
| 进程 `%CPU`、`%MEM` | 定位资源使用较多的进程 |
| `P`、`M` | 分别按 CPU、内存使用排序 |
| `1` | 切换各逻辑 CPU 的显示 |
| `q` | 退出 |

Linux 负载包含可运行任务和部分不可中断等待任务，**不等于 CPU 使用率**。同样的负载值，在不同 CPU 数量的机器上含义不同，应结合核数、等待情况和业务表现判断。

### free：重点看可用内存

```bash
free -h
```

Linux 会利用空闲内存做缓存，所以 `free` 列较小不一定说明内存不足。`available` 估算在不交换的情况下还能供应用使用多少内存，通常更值得关注。

Swap 已有占用也不能单独证明系统正在频繁换页。可以继续查看：

```bash
vmstat 1 5
```

第一行通常是启动以来的平均值，后续是采样间隔数据；结合 `si`、`so` 判断换入换出活动，再观察应用延迟是否同步变化。

## 七、磁盘空间与 I/O 排查

### df：文件系统是否还有空间

```bash
df -h
df -i
```

`df -h` 查看容量，`df -i` 查看 inode 使用情况。大量小文件可能耗尽 inode，即使剩余容量看起来仍然充足，也无法创建新文件。

### du：哪些目录占空间

```bash
sudo du -xhd1 /var
sudo du -xhd1 /var/log
```

在 GNU `du` 中，`-d1` 只展开一层，`-x` 避免跨到其他文件系统，`-h` 使用易读单位。需要查看单个目录总量时：

```bash
du -sh project/
```

与 `du -sh *` 相比，直接统计指定目录不会因为 Shell 的 `*` 默认排除隐藏条目而遗漏它们。

`df` 和 `du` 的统计对象不同，结果不必完全一致。文件已删除但仍被进程打开时，空间也可能暂未释放；安装了 `lsof` 的系统可用 `sudo lsof +L1` 辅助查看。

### iostat：观察设备读写

`iostat` 和 `sar` 通常由 `sysstat` 软件包提供。选择当前系统对应的安装方式：

```bash
sudo apt install sysstat
```

或：

```bash
sudo dnf install sysstat
```

采样观察：

```bash
iostat -xz 1 5
```

重点结合吞吐量、请求等待时间（如 `await`）、队列长度和 `%util`。第一组通常反映启动以来的累计平均，后续才是区间采样。

不要仅凭 `%util` 接近 100% 就断定磁盘达到性能极限。设备并行能力、存储类型和业务延迟都需要一起考虑。

## 八、网络统计与历史数据：sar

查看网络接口和 TCP 的实时统计：

```bash
sar -n DEV 1 5
sar -n TCP,ETCP 1 5
```

`DEV` 可用于观察接口流量；`TCP`、`ETCP` 可辅助观察连接活动和重传等现象。计数变化需要结合采样间隔与业务流量分析。

历史查询依赖系统事先启用数据采集，并保留了对应文件。安装 `sysstat` 并不意味着已经拥有过去的历史数据，采集服务和保存位置也因发行版而异。

## 九、固定 IP：配置前先确认网络管理方式

固定 IP 通常需要同时明确地址与前缀、网关、DNS，以及云平台或虚拟化平台的网络约束。先判断系统由 NetworkManager、Netplan、systemd-networkd 还是其他工具管理网络。

在使用 NetworkManager 的系统上，可先查看：

```bash
nmcli device status
nmcli connection show
```

下面以连接名称 `lab-connection` 为例，展示静态 IPv4 配置格式。地址、网关、DNS 和连接名必须替换为实际值：

```bash
sudo nmcli connection modify 'lab-connection' \
  ipv4.method manual \
  ipv4.addresses '192.168.88.131/24' \
  ipv4.gateway '192.168.88.2' \
  ipv4.dns '192.168.88.2'
```

配置写入后还需要通过适合当前环境的方式应用。激活连接可能中断远程会话，应在有控制台或其他恢复通道的情况下操作，再验证地址、路由和解析结果。

旧教程里的 `/etc/sysconfig/network-scripts/ifcfg-*` 只适用于支持该配置方式的环境，不应当作所有 Linux 系统的统一入口。云主机还可能被 cloud-init 或平台配置覆盖。

## 十、按现象组织排查顺序

### 服务无法访问

```text
服务状态与日志
      ↓
进程是否存在、端口是否监听
      ↓
本机请求是否成功
      ↓
服务器实际地址是否能访问
      ↓
路由、防火墙、安全组、代理与 DNS
```

如果本机请求成功而远程失败，优先比较监听范围和访问路径；如果本机已经返回应用错误，先查应用日志、依赖和路由配置。

### 机器持续变慢

| 顺序 | 查看对象 | 需要回答的问题 |
| --- | --- | --- |
| 1 | `top`、进程列表 | 是哪类资源变化，哪些进程相关？ |
| 2 | `free -h`、`vmstat` | 可用内存是否紧张，是否持续换页？ |
| 3 | `df -h`、`df -i` | 容量或 inode 是否耗尽？ |
| 4 | `iostat`、`sar` | I/O 延迟、吞吐或网络统计是否异常？ |
| 5 | 应用与系统日志 | 指标变化是否与错误、请求高峰或发布对应？ |

不要仅根据一次瞬时采样下结论。保留问题发生的时间、进程信息与相关日志，才能把资源指标和实际影响对应起来。

## 十一、命令速查

| 命令 | 用途 |
| --- | --- |
| `ip -br addr` | 查看接口与地址概况 |
| `ip route` | 查看 IPv4 路由 |
| `getent ahosts 域名` | 按系统规则查询名称解析 |
| `ping -c 4 地址` | 测试 ICMP 回应 |
| `curl -i URL` | 查看 HTTP 响应头和正文 |
| `sudo ss -lntp 'sport = :8080'` | 查看 TCP 8080 监听及关联进程 |
| `pgrep -af 关键字` | 查找匹配命令行的进程 |
| `ps -p 1234 -f` | 查看指定进程 |
| `top`、`free -h` | 观察进程、CPU 与内存 |
| `df -h`、`df -i` | 查看容量与 inode |
| `du -xhd1 目录` | 查看一层目录占用，限制在同一文件系统 |
| `iostat -xz 1 5` | 连续采样磁盘 I/O |
| `sar -n DEV 1 5` | 连续采样网卡统计 |
