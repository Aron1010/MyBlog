> [系列导读](../00-系列导读.md) · 第 2 章：把需求说清楚

第一章已经用几类文字任务建立了使用直觉。现在把每一类任务的输入、约束和检查点写完整。

“帮我处理一下这段文字”可以产生很多结果：重写、缩短、整理要点，甚至扩写一份方案。但如果没有说明要做什么，很难判断模型究竟有没有完成任务。

大语言模型可以辅助多种语言处理工作。本篇仍把需求分为四类：生成、改写、提取和分类。这不是全部能力的清单，而是一组便于明确目标、检查结果的入口。[Hugging Face 的课程介绍](https://huggingface.co/learn/llm-course/en/chapter1/1)讨论了语言模型与语言处理任务的关系。

## 一、先准备一份共同材料

以下通知是虚构的教学材料，后面的参考结果由人工编写，不是某个模型的实测输出。

> 第一轮讨论安排在周五下午三点，线上进行，主题是“怎样阅读技术文章”。请小林提前整理三条阅读要点。报名截止时间为周四晚上八点。主持人尚未确定。

这段材料已经给出了部分事实，也留下了明确的空缺：没有具体年月日、没有会议链接，主持人还没定。

它是第一章 N01 笔记中的活动安排片段。这里把它单独取出，方便比较几类任务；实际做前后比较时，应保留同一份材料。

明确这些边界之后，我们才能区分“合理组织语言”和“没有依据地补充事实”。

## 二、生成：根据事实与要求起草内容

生成任务允许模型组织新的表达，例如把事实要点写成一则通知。但新增表达与新增事实应当区分。

可以这样描述任务：

```text
请根据下面的材料起草一则读书会通知。

读者：第一次参加活动的同学。
语气：自然、清楚，不使用夸张宣传语。
内容：交代时间、形式、主题、报名截止时间和准备事项。
约束：不得编造具体年月日、会议链接、报名渠道或主持人。
输出：一个标题和两段正文；缺少的报名渠道请单独列为待补充项。

材料：
第一轮讨论安排在周五下午三点，线上进行，主题是“怎样阅读技术文章”。
请小林提前整理三条阅读要点。报名截止时间为周四晚上八点。主持人尚未确定。
```

检查时，除了看文案是否适合读者，还要检查“小林准备三条阅读要点”有没有被扩大成“所有同学都必须提交三条阅读要点”。后者改变了原始要求。

模型还可能写出一个很常见但无依据的句子，例如“点击群公告链接即可报名”。文字自然，却补出了不存在的渠道。

## 三、改写：允许变化的是表达

改写任务可以调整语气、长度和结构，但关键事实及其确定程度应保留。

例如，把通知压缩成一段提醒：

```text
请把材料改写为一段简洁提醒。
必须保留：讨论时间、线上形式、主题、报名截止时间、小林的准备事项，以及主持人尚未确定。
允许调整顺序和措辞，不得新增事实或把待定事项改为确定安排。
```

一份人工参考写法是：

> 周五下午三点线上讨论“怎样阅读技术文章”，报名截止到周四晚上八点。请小林提前整理三条阅读要点，主持人尚未确定。

如果改写结果只剩“周五有线上讨论，欢迎参加”，就遗漏了多个关键条件。改写是否完成，不能只用“更短了”评价。

如果长度与信息完整性发生冲突，可以让模型说明取舍，或者先确定必须保留的信息，再放宽篇幅。

## 四、提取：让每个字段都能回到原文

信息提取适合把邮件、通知或记录整理成固定字段。可以明确规定缺失值，而不是期待模型自行决定怎样补齐。

```text
只依据材料提取以下字段：
讨论时间、具体日期、形式、主题、报名截止时间、准备事项、准备事项负责人、主持人。

输出为两列表格：字段、结果。
没有明确给出的信息写“未提供”。
明确待定的信息写“待定”。
不要根据当前日期推算“周五”的年月日，也不要把准备事项负责人当成主持人。
```

对应的人工参考结果是：

| 字段 | 结果 |
| --- | --- |
| 讨论时间 | 周五下午三点 |
| 具体日期 | 未提供 |
| 形式 | 线上 |
| 主题 | 怎样阅读技术文章 |
| 报名截止时间 | 周四晚上八点 |
| 准备事项 | 提前整理三条阅读要点 |
| 准备事项负责人 | 小林 |
| 主持人 | 待定 |

如果还需要把结果交给程序，可以要求 JSON 等结构。不过，输出看起来像 JSON，与它能通过解析、字段完整、内容准确，是不同的检查项。

## 五、分类：先给类别下定义

假设要整理读者反馈，可以使用以下类别：

| 类别 | 定义 |
| --- | --- |
| 内容建议 | 对知识点、例子、解释顺序或深度提出意见 |
| 排版建议 | 对字号、图表布局、段落或页面显示提出意见 |
| 其他 | 不属于前两类的反馈 |

再明确：一条反馈允许有多个标签；只有前两类都不适用时，才使用“其他”。

对于“例子还可以再多一点，手机上的表格也太宽了”，人工参考标签应是“内容建议、排版建议”。如果要求只能选一类，就还需要制定优先级，否则所谓标准答案本身就可能不明确。

分类错误有时来自模型没有遵守定义，有时来自定义本身重叠或含糊。先修正标准，再比较输出，通常更容易定位问题。

## 六、任务可以组合，但每一步应保留检查点

处理一篇长会议记录，可以先提取决定、待办和未决事项，再根据这些结果生成通知，最后回到原文逐项核对。

拆成几步能让过程更容易检查，却不会自动消除错误。第一步把负责人提错，后面的通知也可能沿用错误。所以，中间结果值得保留，特别是姓名、日期、金额和确定程度等字段。

| 任务 | 检查重点 |
| --- | --- |
| 生成 | 是否满足用途、事实和输出要求 |
| 改写 | 是否保留原意、关键条件与不确定性 |
| 提取 | 每一项能否在原文中找到依据 |
| 分类 | 是否符合类别定义与多标签规则 |

## 七、一个可以复用的任务说明

```text
任务：我希望你完成什么。
材料：本次可以依据哪些内容。
要求：必须保留哪些事实，允许改变什么。
缺失处理：资料不足时怎样标记，是否需要向我提问。
输出：结构、长度、字段或格式。
检查：哪些地方必须能逐项回到原文。
```

这个模板的作用是让标准更清楚，不是某种保证正确的特殊咒语。对于重复使用的任务，还应该准备一批代表性材料和人工标注结果，记录常见错误，再决定是否值得放入日常流程。

从容易核对、即使出错也方便修正的小任务开始，更容易积累判断模型能力的经验。后续会比较加入例子、调整上下文和限定输出格式的效果。每次修改都保留同一组问题，才能知道变化来自哪里。


## 八、保留材料与处理过程

本篇取出了 N01 笔记的活动安排片段。第一章的[笔记整理案例](../01-认识大语言模型/06-一份笔记的整理过程.md)展示了完整材料怎样形成阅读要点、安排表和缺失信息，两者对应不同的处理范围。

应用开发中比较任务说明的效果，需要保留输入材料、原始输出和运行条件。材料或任务发生变化时，也应记录，避免把不同条件下的结果直接混在一起。

需要检查事实边界时，可以对照第一章的[幻觉与事实核对](../01-认识大语言模型/05-幻觉与事实核对.md)。
