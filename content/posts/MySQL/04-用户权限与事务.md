> [MySQL 入门指南](./00-MySQL入门指南.md) · 第四章：明确谁能操作，以及一组修改何时生效。

账号权限回答“允许执行哪些操作”，事务回答“这些数据修改如何成为一个整体”。两者都需要明确边界：有权限不代表业务操作正确，开启事务也不代表程序中的任何错误都会自动撤销全部修改。

以下事务说明以 InnoDB 为前提。账号管理示例需要相应管理权限，并且不属于核心表的初始化步骤。

## 一、账号由用户名与来源共同标识

```sql
SELECT USER() AS connection_identity,
       CURRENT_USER() AS matched_account;
```

`USER()` 展示连接提交的用户名与来源信息，`CURRENT_USER()` 在普通会话中可用于确认匹配的认证账号。执行具有定义者上下文的对象时，还要考虑其安全上下文。

`'report_user'@'localhost'` 和 `'report_user'@'192.168.1.10'` 是不同账号。Host 描述服务器看到的客户端来源，不是数据库服务器自己的地址。

查看账号需要管理权限：

```sql
SELECT User, Host FROM mysql.user;
```

操作系统 root 与 MySQL root 是不同身份。连接方式、认证插件和系统集成可能让它们产生关联，但不能直接等同。

## 二、创建账号、授权与角色

### 创建和修改密码

下面密码字符串必须替换，不能当作实际密码使用：

```sql
CREATE USER 'report_user'@'localhost'
IDENTIFIED BY 'REPLACE_WITH_A_UNIQUE_STRONG_PASSWORD';

ALTER USER 'report_user'@'localhost'
IDENTIFIED BY 'REPLACE_WITH_ANOTHER_STRONG_PASSWORD';
```

一般让服务器按正常配置选择认证方式，再使用支持该方式的客户端。MySQL 8.4 默认禁用旧的 `mysql_native_password`，不要为了兼容老教程而把切换旧插件当作默认解决方案。

### 按工作需求授权

```sql
GRANT SELECT ON mysql_learn.*
TO 'report_user'@'localhost';

SHOW GRANTS FOR 'report_user'@'localhost';
```

应用账号可以使用更明确的来源和表范围，例如：

```sql
CREATE USER 'app_user'@'127.0.0.1'
IDENTIFIED BY 'REPLACE_WITH_A_UNIQUE_APPLICATION_PASSWORD';

GRANT SELECT, INSERT, UPDATE, DELETE ON mysql_learn.emp
TO 'app_user'@'127.0.0.1';

GRANT SELECT ON mysql_learn.dept
TO 'app_user'@'127.0.0.1';
```

这是本机 TCP 应用的账号示例。实际 Host 匹配还受来源和名称解析等条件影响，远程部署应使用服务器实际看到的来源范围。`%` 等通配来源范围很大，且涉及版本兼容问题，不应无条件复制到授权规则中。

`GRANT` 不代替 `CREATE USER` 创建账号。应用日常读写通常不需要建库、删表或给其他用户授权。

### 角色：集中维护一组权限

下面展示角色授权的另一种组织方式，可根据实际需求选择：

```sql
CREATE ROLE 'mysql_learn_reader';
GRANT SELECT ON mysql_learn.* TO 'mysql_learn_reader';
GRANT 'mysql_learn_reader' TO 'report_user'@'localhost';
SET DEFAULT ROLE 'mysql_learn_reader'
TO 'report_user'@'localhost';
```

授予角色与激活角色是不同步骤。角色和直接权限可以同时存在；移除某条授权不一定消除通过其他来源获得的同类权限。

### 回收与停用

以下是按需执行的管理语法，不要在仍需要账号时一起顺序执行：

```sql
REVOKE UPDATE, DELETE ON mysql_learn.emp
FROM 'app_user'@'127.0.0.1';

ALTER USER 'report_user'@'localhost' ACCOUNT LOCK;
```

删除账号使用 `DROP USER '用户名'@'来源';`。锁定或删除账号不应被当作自动终止所有已有会话的替代，需要同时检查现有连接与业务影响。

通过正常的账号管理语句修改权限后，通常不需要再执行 `FLUSH PRIVILEGES`。不要直接修改系统授权表来代替管理语句。

## 三、事务、自动提交与显式边界

```sql
SELECT @@session.autocommit;
```

自动提交开启时，一条独立的事务性语句通常自成一个事务。需要把多条修改组合起来时，可以显式开启：

```sql
START TRANSACTION;

UPDATE emp SET salary = salary + 100.00 WHERE id = 2;
SELECT id, salary FROM emp WHERE id = 2;

ROLLBACK;
```

`COMMIT` 提交，`ROLLBACK` 撤销当前事务未提交的事务性修改。上例回滚以保留固定数据。

| 操作 | 边界含义 |
| --- | --- |
| `START TRANSACTION` | 开始显式事务 |
| `COMMIT` | 提交并结束当前事务 |
| `ROLLBACK` | 回滚并结束当前事务 |
| `SET autocommit = 0` | 改变会话后续的自动提交方式 |

MySQL 不支持通过再次 `START TRANSACTION` 创建真正的嵌套事务；它可能提交之前的事务。把 `autocommit` 从 0 切回 1 也可能提交未完成的事务，不能当作无影响的环境恢复动作。

一条语句报错后，之前的成功修改不一定全部回滚。普通约束错误通常只回滚失败语句，死锁可能回滚整个事务。应用必须明确处理异常与事务结束，不能继续执行后直接提交。

## 四、SAVEPOINT：撤销局部步骤

```sql
START TRANSACTION;

UPDATE emp SET salary = salary + 100.00 WHERE id = 2;
SAVEPOINT after_salary;

UPDATE emp SET nickname = '临时昵称' WHERE id = 2;
ROLLBACK TO SAVEPOINT after_salary;
RELEASE SAVEPOINT after_salary;

SELECT id, nickname, salary FROM emp WHERE id = 2;
ROLLBACK;
```

回到保存点后，薪资修改仍存在于当前事务，昵称修改被撤销；最后再整体回滚，固定数据保持原值。

保存点不等于独立子事务，回滚到保存点不会结束外层事务，也不能假设所有锁和相关资源都完整恢复到保存点之前的状态。

## 五、ACID 的实际含义

| 特性 | 关注点 |
| --- | --- |
| 原子性 Atomicity | 已纳入事务的修改按边界提交或撤销 |
| 一致性 Consistency | 修改前后满足定义的约束和业务不变量 |
| 隔离性 Isolation | 并发事务按约定规则看到和影响彼此的数据 |
| 持久性 Durability | 成功提交的数据按系统承诺保存并参与故障恢复 |

事务不能替程序自动定义全部业务规则。例如数据库可以保证余额非负，但不能自动知道同一请求是否被重复扣款，也不能自动回滚已经发出的短信。

持久性还依赖日志刷盘策略、存储可靠性等条件。提交成功也不能替代备份，尤其不能解决之后发生的误删或错误更新。

## 六、隔离级别与不同读取方式

| 隔离级别 | 脏读 | 不可重复读 | 幻读，按 SQL 标准可能性 |
| --- | --- | --- | --- |
| `READ UNCOMMITTED` | 可能 | 可能 | 可能 |
| `READ COMMITTED` | 避免 | 可能 | 可能 |
| `REPEATABLE READ` | 避免 | 避免 | 可能 |
| `SERIALIZABLE` | 避免 | 避免 | 避免 |

脏读是读取未提交数据；不可重复读关注同一行的值发生变化；幻读关注按条件得到的行集合发生变化。

InnoDB 默认通常为 `REPEATABLE READ`，但实例配置可能修改它：

```sql
SELECT @@session.transaction_isolation;
```

在没有活动事务时，可以为后续事务设置会话隔离级别：

```sql
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;
```

### 一致性读：按快照查看

在 REPEATABLE READ 下，普通一致性读通常使用事务第一次这类读取建立的快照，而不是简单按 `START TRANSACTION` 的时间建立。READ COMMITTED 通常每次一致性读建立新快照。

事务也会看到自己的修改，因此“快照”不能简单理解为事务中所有语句永远只看到一个完全冻结的世界。

### 锁定读：获取用于修改判断的当前数据

```sql
START TRANSACTION;
SELECT id, salary FROM emp WHERE id = 2 FOR UPDATE;
ROLLBACK;
```

`FOR UPDATE` 用于排他锁定读，可能等待其他事务释放冲突锁。必须把读取和后续修改放在正确的事务边界内，否则锁可能立即释放，无法保护后续判断。

InnoDB 通过 MVCC 和锁机制处理并发；锁范围还取决于索引、条件与隔离级别。不能只凭“使用了行锁”就认定只会锁定业务上预想的一行。

## 七、转账示例：必须检查每一步

单独创建本节账户表并写入一次数据：

```sql
CREATE TABLE account (
    id BIGINT UNSIGNED NOT NULL,
    owner_name VARCHAR(50) NOT NULL,
    balance DECIMAL(12,2) NOT NULL,
    PRIMARY KEY (id),
    CONSTRAINT chk_account_balance CHECK (balance >= 0)
) ENGINE = InnoDB;

INSERT INTO account (id, owner_name, balance)
VALUES (1, '付款方', 1000.00), (2, '收款方', 500.00);
```

完整控制流程应由应用或经过正确编写的存储程序执行：

```text
确认金额为正，付款方与收款方不同
开始事务
按统一主键顺序锁定两个账户，确认两者都存在
执行带余额条件的扣款
如果影响行数不是 1：回滚并停止
执行收款方入账
如果影响行数不是 1：回滚并停止
记录可唯一识别本次业务的流水
提交；任一步异常时按错误类型回滚与处理
```

关键扣款语句如下，必须放在上述控制流程中：

```sql
UPDATE account
SET balance = balance - 100.00
WHERE id = 1 AND balance >= 100.00;
```

紧随其后的 `SELECT ROW_COUNT();` 可在客户端查看该语句的影响行数，应用通常直接读取驱动返回值。**扣款没有成功时不能继续给收款方入账。**

多账户操作应按统一顺序逐个锁定，例如始终先锁较小主键，再锁较大主键。单纯在一个复杂查询中写 `ORDER BY`，不等于在所有执行计划下都获得同样的实际加锁顺序。

上面的片段只说明关键逻辑，不是可以无条件接上 COMMIT 的完整转账脚本。生产流程还需要幂等标识、流水、失败重试和审计。

## 八、死锁、超时与长事务

| 现象 | 理解与处理 |
| --- | --- |
| 死锁 | 数据库检测到循环等待，会选择事务回滚；按业务可重试范围重试整个事务 |
| 锁等待超时 | 等待超过限制，回滚范围与配置有关；应用应结束当前失败流程并清理事务 |
| 长事务 | 可能长期持锁、保留旧版本并阻碍清理 |
| 提交时连接中断 | 客户端可能无法确认最终是否提交，不能直接把“未收到回应”当作“未生效” |

事务尽量短，避免在持锁期间等待用户输入、调用外部接口或处理大型文件。出现冲突时，应同时检查访问顺序、索引和事务范围，不只是不断增加超时。

`CREATE`、`ALTER`、`DROP`、`TRUNCATE` 以及许多账号管理语句会引发隐式提交。不要把 DDL 或授权修改混进普通业务事务后期待统一回滚。

## 九、语句速查

| 语句 | 用途 |
| --- | --- |
| `SHOW GRANTS FOR '用户'@'来源'` | 查看授权 |
| `CREATE USER ... IDENTIFIED BY ...` | 创建账号 |
| `GRANT 权限 ON 对象 TO 账号` | 授权 |
| `REVOKE 权限 ON 对象 FROM 账号` | 回收指定授权 |
| `START TRANSACTION` | 开启显式事务 |
| `COMMIT`、`ROLLBACK` | 提交、回滚 |
| `SAVEPOINT 名称` | 设置保存点 |
| `ROLLBACK TO SAVEPOINT 名称` | 撤销保存点之后的事务性修改 |
| `SELECT ... FOR UPDATE` | 进行锁定读 |
